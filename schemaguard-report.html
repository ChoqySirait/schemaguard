🛡️ Strategi Mitigasi Transisi Aman (Pola Expand-Contract)

#1 Mitigasi Zero-Downtime untuk DROP COLUMN 'users.avatar_url' Target: users.avatar_url

Penghapusan kolom 'avatar_url' langsung akan memicu galat runtime kueri (e.g. SELECT * atau INSERT eksplisit) pada aplikasi versi sebelumnya yang masih beroperasi.

Fase 1: Expand (Perluas)

Fase Perluas (Expand): Penghapusan Akses pada Lapisan Aplikasi

Pertahankan kolom 'avatar_url' pada skema fisik, namun hentikan seluruh akses pembacaan dan penulisan dari aplikasi.

-- Pastikan kolom bersifat nullable agar aplikasi versi lama tidak gagal saat tidak mengisi kolom ini
ALTER TABLE users ALTER COLUMN avatar_url DROP NOT NULL;
COMMENT ON COLUMN users.avatar_url IS 'DEPRECATED: Kolom tidak lagi digunakan oleh aplikasi aktif.';
Fase 2: Contract (Susutkan)

Fase Susutkan (Contract): Penghapusan Kolom Fisik dari Skema

Hapus kolom 'avatar_url' setelah seluruh pod atau instance aplikasi versi baru berjalan penuh.

-- Kolom aman dihapus karena kode produksi sudah 100% tidak lagi membaca atau menulis kolom ini
ALTER TABLE users DROP COLUMN IF EXISTS avatar_url;
📋 Catatan Transisi & Panduan Penerapan:
  • Rilis v1: Modifikasi kode aplikasi agar tidak menyertakan kolom 'avatar_url' dalam skema ORM, SELECT, atau INSERT.
  • Lakukan deployment kode v1 hingga 100% armada server selesai diperbarui.
  • Rilis v2: Eksekusi skrip fase Contract pada skema basis data.
#2 Mitigasi Zero-Downtime untuk ALTER COLUMN TYPE 'users.age' ke 'BIGINT' Target: users.age

Mengubah tipe data kolom secara langsung menyebabkan table lock eksklusif serta kegagalan konversi tipe instan pada baris berjumlah besar.

Fase 1: Expand (Perluas)

Fase Perluas (Expand): Tambah Kolom Baru, Pasang Pemicu Sinkronisasi, dan Backfill Bertahap

Tambahkan kolom 'age_new' dengan tipe 'BIGINT', aktifkan pemicu sinkronisasi ganda (dual-writing) terlebih dahulu untuk menangkap transaksi baru, lalu lakukan backfill data historis dalam batch kecil.

-- Langkah 1: Tambahkan kolom bayangan baru dengan tipe target
ALTER TABLE users ADD COLUMN IF NOT EXISTS age_new BIGINT;

-- Langkah 2: Pasang pemicu sinkronisasi ganda (dual-writing) TERLEBIH DAHULU untuk menangkap transaksi data baru
CREATE OR REPLACE FUNCTION sync_users_age() RETURNS TRIGGER AS $$
BEGIN
  NEW.age_new := CAST(NEW.age AS BIGINT);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE OR REPLACE TRIGGER trg_sync_users_age
BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION sync_users_age();

-- Langkah 3: Backfill data historis lama secara bertahap (1.000-5.000 baris per batch berpaginasi untuk mencegah lock)
-- Jalankan kueri batch berikut berulang hingga 0 baris terpengaruh:
UPDATE users
SET age_new = CAST(age AS BIGINT)
WHERE id IN (
  SELECT id FROM users
  WHERE age_new IS NULL
  ORDER BY id
  LIMIT 5000
);
Fase 2: Contract (Susutkan)

Fase Susutkan (Contract): Alihkan Pembacaan, Hapus Kolom Lama, dan Ganti Nama

Setelah seluruh aplikasi membaca 'age_new', bersihkan trigger sinkronisasi dan ganti nama kolom menjadi nama asli.

-- Langkah 1: Hapus trigger sinkronisasi
DROP TRIGGER IF EXISTS trg_sync_users_age ON users;
DROP FUNCTION IF EXISTS sync_users_age();

-- Langkah 2: Hapus kolom lama
ALTER TABLE users DROP COLUMN age;

-- Langkah 3: Ganti nama kolom bayangan menjadi nama definitif
ALTER TABLE users RENAME COLUMN age_new TO age;
📋 Catatan Transisi & Panduan Penerapan:
  • Terapkan aplikasi versi A: Mendukung penulisan ganda (dual-writing) ke 'age' dan 'age_new'.
  • Jalankan skrip migrasi backfill dalam batch kecil (misal: LIMIT 1000) untuk menghindari saturasi I/O basis data.
  • Terapkan aplikasi versi B: Alihkan pembacaan (reads) sepenuhnya ke 'age_new'.
  • Jalankan skrip fase Contract untuk merapikan skema.
#3 Mitigasi Pembuatan Indeks Tanpa Kunci untuk 'idx_orders_user' pada 'orders' Target: orders (idx_orders_user)

Pembuatan indeks standar mengunci tabel untuk operasi tulis sampai proses indeks selesai, memicu lonjakan latensi atau timeout di produksi.

Fase 1: Expand (Perluas)

Fase Perluas (Expand): Buat Indeks Menggunakan Mode Non-Pemblokiran (CONCURRENTLY)

Gunakan instruksi CONCURRENTLY agar proses pengindeksan tidak mengunci operasi INSERT/UPDATE/DELETE pada tabel.

-- Buat indeks di luar blok transaksi (PostgreSQL CONCURRENTLY)
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_user ON orders (user_id);
Fase 2: Contract (Susutkan)

Fase Susutkan (Contract): Verifikasi Status Keabsahan Indeks

Pastikan indeks berhasil dibuat dengan status valid dan siap digunakan oleh perencana kueri.

-- Periksa apakah indeks berstatus valid (PostgreSQL)
SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE indexrelid = 'idx_orders_user'::regclass;
-- Jika indisvalid bernilai false, jalankan: REINDEX INDEX CONCURRENTLY idx_orders_user;
📋 Catatan Transisi & Panduan Penerapan:
  • Eksekusi pembuatan indeks CONCURRENTLY harus dijalankan di luar blok transaksi tunggal (autocommit aktif).
  • Pantau metrik CPU dan Disk I/O selama proses pembuatan indeks berjalan.
  • Jika pembuatan indeks dibatalkan di tengah jalan, bersihkan indeks tidak valid sebelum mencoba kembali.
